# Native project assignments

Project assignments extend durable Group runs, child identities and dispatch attempts. These owner-only routes use the existing paired-session/CSRF or local capability boundary. They are not runtime Bot tools and never accept caller-provided credentials or an arbitrary repository path.

- `GET /api/v1/groups/{groupId}/assignment-projects` returns `{projects:[{botId,projectName,baseRevision}]}` for eligible specialists with already-authorized project write access. The revision is the full current commit.
- `GET /api/v1/groups/{groupId}/assignments` returns `{assignments:[...]}`, newest first, bounded to 100 results.
- `POST /api/v1/groups/{groupId}/assignments` accepts `{clientRequestId,title,instruction,botId,baseRevision,dependencyIds}`. The UUID is required and immutable across retries. Dependencies default to `[]` and must already exist in the same Group/repository. The repository is the Bot's configured project root; its checked-out branch is fixed at acceptance. Detached projects must check out a branch first.
- `GET /api/v1/assignments/{id}` returns assignment details, the full bounded Git diff, branch, `targetBranch`, worktree/repository paths and `repositoryHead`. Paths belong in deliberate details only.
- `POST /api/v1/assignments/{id}/review` accepts `{resultRevision,validation}`. Validation records the owner's review evidence; it does not assert daemon-run tests. A changed or dirty result is rejected. The same recorded review is idempotent.
- `POST /api/v1/assignments/{id}/integrate` accepts `{resultRevision,expectedHead}`. Only a reviewed, clean worktree may advance the original project branch from its exact base by fast-forward. A changed checkout is rejected even when its commit is identical. Divergence requires new work and review. Integration intent is persisted before Git; retry recognizes the exact resulting HEAD after a completed Git update and an interrupted status commit. Git-native HEAD/ref and index locks protect the checkout update from external Git writers. Interruption during the file/index/ref boundary preserves the prepared index and stays `integrating`; inspect and recover on the Mac before retrying, without automatically removing locks or overwriting edits.
- `POST /api/v1/assignments/{id}/cancel` cancels queued work. `canCancel` advertises this capability. Running work uses the existing Bot Stop path; cancellation does not imply rollback of edits.

Create and mutation responses are bare assignment objects. Ordinary objects contain `id`, `groupId`, `botId`, `title`, `projectName`, `instruction`, `state`, `baseRevision`, nullable `resultRevision`, nullable `summary`, nullable `validation`, `dependencyIds`, `createdAt`, `updatedAt`, and `canCancel`. Timestamp strings use existing daemon conventions (ISO creation; epoch milliseconds on state updates). Detail additionally contains `branch`, `targetBranch`, `worktreePath`, `repositoryPath`, `repositoryHead`, and `diff` when a result is submitted. An oversized/unavailable diff returns an actionable error instead of a partial patch eligible for review.

State names are `queued`, `working`, `awaiting_input`, `submitted`, `reviewed`, `integrating`, `integrated`, `failed`, `cancelled`, and `uncertain`. The existing approval/question surface remains authoritative; `awaiting_input` is reserved for explicit assignment projection. Submitted or reviewed results do not unlock dependencies. Once dependencies are integrated, execution pins their actual descendant result revision before creating the worktree.

The first version supports verified native Workspace and Full access modes. It does not silently widen custom or read-only profiles. Each worktree is inside the specialist Bot's private workspace, and the original repository must already be authorized for writes. The Bot's ordinary working directory is unchanged. Both first dispatch and ambiguous-submission reconciliation resolve the durable assignment context. A completed Bot turn is not a submitted assignment until a clean committed descendant revision is verified.

Acceptance still requires the installed native journey, independent review, pending-question/Stop behavior and real owner-created work. The coordinator runtime tools below are implemented separately from these owner routes; installed PM delegation still needs end-to-end acceptance.

Terminal assignment outcomes reconcile their Group parents before dispatch. Assignment readiness and integrated dependencies are filtered before the bounded pending-run limit, so blocked work cannot starve unrelated messages. Group deletion clears assignment metadata transactionally and retains repository worktrees; it is unavailable during integration or unresolved integration recovery. The existing explicitly destructive full workspace reset removes assignment metadata and follows its existing Bot-home deletion behavior, including assignment folders within those homes. Git worktree registrations are not pruned automatically.

## Coordinator runtime tools

A coordinator in its actual Group conversation receives three registered tools: `wonder_list_assignments`, `wonder_assign_project`, and `wonder_inspect_assignment`. The owner can address the coordinator directly (for example, `@PM`) to request bounded project work. Existing ordinary broadcast behavior is unchanged. There is no wait tool: the coordinator creates work and finishes its response before queued specialists can begin. Review and integration remain owner actions.

The tool boundary derives Group, owner and coordinator identity from the live runtime, exact thread/turn message, Group node and immutable accepted Group snapshot. It requires the current registered Group thread and the repository/write permission recorded at dispatch. The coordinator and specialist must use the same approved repository. Arguments cannot supply owner credentials, Group authority or a different repository path. Old coordinator threads migrate to the new tool registration before their next turn; computer-use registration and approvals stay separate.

`wonder_list_assignments({})` returns compact assignment summaries plus eligible specialist projects and full base revisions. `wonder_assign_project` takes the same creation fields as owner creation (including a stable `clientRequestId`), without a Group ID. Its response confirms durable acceptance and directs the coordinator to finish the current response. `wonder_inspect_assignment({assignmentId})` returns the authorized assignment and a bounded submitted diff. Each coordinator message has a 16-call limit; tool responses are bounded to 1 MiB. No tool approves, reviews, merges, deploys, sends owner credentials or starts a second scheduler.

Migration0051 records the actual runtime/call/thread/turn identity and input hash before execution, then persists the complete tool response before transport delivery. Re-delivery reuses the stored response. If assignment creation commits before response persistence, retry uses the existing immutable creation UUID and cannot create another assignment. Deleting the owning message cascades the call ledger so ordinary Group/reset cleanup remains valid. Dead runtime transports cannot execute recorded calls on restart.
